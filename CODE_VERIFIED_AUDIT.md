## 0. Database-layer fix pass (2026-09-08, second session)

At the user's request, the database/connection layer was rebuilt properly rather than left as a punch list. This section documents what changed and what's still open. **Sections 1–5 below describe the *original* state of the code and are kept for history — several of the specific bugs they cite (marked below) are now fixed in source.** `docker/` was updated to match and the whole stack was rebuilt and re-tested live in the container after every change in this section (not just read/reasoned about).

### 0.1 What was fixed

- **Connection pooling, made real instead of accidental.** `ConnectionPool` (`postgresbc.cpp`) is a singleton whose `initialize()` only takes effect on its first call per process — every subsequent `Postgresql(user, password, ...)` construction silently reuses whatever connection the *first* caller happened to establish, regardless of the credentials passed to its own constructor. Previously this fired lazily, seeded by whichever command handler ran first (in practice, always `check_user_credentials()`'s service-account connection). `main()` now calls `ConnectionPool::getInstance().initialize(...)` explicitly, once, with the configured service account, immediately after reading config — before any command handler or the credentials check can run. Same runtime behavior as before, but now an intentional, guaranteed design rather than an implementation accident (see §0.3 for the security implication this resolves).
- **Transactions, wired up rather than dormant.** `beginTransaction()`/`commitTransaction()`/`rollbackTransaction()` already existed in `postgresbc.cpp` but were never called anywhere in `main.cpp`, and independently would have hung/misbehaved because they routed through `OmniIndex::Utils::Logging::log()` — which makes its *own* pooled DB call and, per six separate comments elsewhere in the same file, "hangs indefinitely." Replaced those calls with `std::cerr` logging (consistent with the rest of the file) and now wrap every genuinely multi-statement write in a transaction: `cash_up()` (mark all period_sales rows closed + insert the cash_up row), `update_sale()` (close prior row + insert new running-total row), `move_stock_in()`/`move_stock_out()` (stock_removal row + stock upsert).
- **Parameterized queries everywhere.** Every SQL statement in `main.cpp` that concatenated caller-supplied or DB-round-tripped values directly into the query text (the systemic SQL injection from the original audit, §3.1 below) now uses `PQexecParams` via two new `Postgresql` methods, `runCommandParams()`/`execParams()` (`postgresbc.cpp`/`.h`). Same fix applied to `authentication.cpp` (`authenticate()`, `getUserById()`, `getUserByUsername()`, `hasRole()`, `verifyPassword()`, `updateLastLogin()`) and `logging.cpp`. This also incidentally eliminated an entire class of "missing/misplaced quote produces malformed SQL" bugs that existed alongside the injection risk (see §0.2).
- **Auth trail fixed:**
  - Removed the `is_white_listed = true;` unconditional override (`main.cpp`) and the broken "whitelist" logic above it, which checked `SERVER_NAME` (the serving host's own name — constant for every request, not the caller's identity) rather than the caller's actual address, and which — bug or not — let any request that simply omitted `username`/`password` silently authenticate as the configured `epos_user` service account. Every command now requires real credentials; verified live (`{"error": "username and or password not found"}` with no credentials, where it previously auto-authenticated).
  - `Authentication::authenticate()` used to hardcode `result["role"] = "admin"` and `result["id"] = "1"` for *any* successful login. Now genuinely parses the row the query returned. Verified live: `login` for the seeded admin account now returns the real `email`/`role`/`full_name` from `store.users`, not a fixed placeholder.
  - `Authentication::hasRole()` used to run its `COUNT(*)` query and discard the result, unconditionally returning `true`. `verifyPassword()` used to run a `SELECT COUNT(*)` through `exec()`, which reports `PGRES_COMMAND_OK` vs. not — a `SELECT` always comes back `PGRES_TUPLES_OK`, so this function always returned `false` regardless of whether the password matched. Both now genuinely check the query's actual result.
  - Removed the requirement (previously true only by accident of the connection-pool bug above) that every application user also exist as a literal PostgreSQL login role with a matching plaintext password. All queries now run through the single pre-initialized service-account connection; a caller's own username/password is checked only against `store.users` (bcrypt via pgcrypto), never used as a Postgres connection credential.
  - `add_user()`'s customer password was stored in **plaintext** in `store.customers.password`; now hashed with the same pgcrypto `crypt()`/`gen_salt('bf')` scheme as `store.users`.
  - The service account's plaintext DB password was being written to stderr on every login attempt (`main.cpp`, `[LOGIN] Config loaded: ... password=...`); removed.
- **Schema fixed to standard PostgreSQL**, in the real tracked `code/sql/setup.sql` and `code/sql/add_admin.sql` (not just a container-only patch): `CREATE USER IF NOT EXISTS` (invalid syntax — Postgres has no such clause) replaced with the idiomatic `DO $$ ... IF NOT EXISTS (SELECT FROM pg_roles ...) ... $$` pattern, and the hardcoded plaintext password removed from the file entirely (a real deployment sets it separately — `docker/` templates this from an env var for local use); the MySQL-style inline `INDEX(...)` clauses in `period_sales` replaced with standalone `CREATE INDEX` statements; `pg_trgm`/`fuzzystrmatch`/`uuid-ossp` extension creation moved before their first use (the products table's trigram indexes need `pg_trgm` to already exist — this failed outright against real Postgres as shipped); `add_admin.sql`'s broken `<email>`/`<PASSWORD>` placeholders and unclosed-string-literal `crypt()` call replaced with proper `psql` variable substitution.
- **`docker/`** rebuilt to match: the schema/auth fixes are now in the real source, so the Docker-build-time source patches from the first pass (sed-patching `modified_date`, seeding extra native Postgres roles per app user) are gone — Docker now just builds and runs the actual fixed source, with container-only concerns (setting the `store` role's password, seeding demo users/products) kept clearly separate and commented as such. Full stack rebuilt from a wiped volume and re-tested; every command below was actually exercised against the running container, not just read.

### 0.2 Bugs found (and fixed) only by actually running the fixed code against real data

These did not surface from reading the code — they only appeared once the parameterized queries and real schema were exercised end to end:

- **`sellitem` didn't decrement stock at all**, even though it reported success. `update_sale()`'s `quantity` parameter (the actual units sold) was being overwritten with the *previous* period_sales row's stored quantity before being handed to `update_stock()` — so every sale adjusted stock by the prior cumulative count (or by "0" on a product's first sale), never by the units actually sold. Fixed by keeping a separate `sale_quantity` that preserves the real per-sale figure. Verified live: repeated sales of the same barcode now decrement stock by the correct amount each time (50 → 49 → 47 → 46 across three sales of 1, 2, then 1 unit).
- **A sale immediately after `cashup` was silently rejected.** `update_sale()`'s `completed == "0"` branch (meaning the barcode's last period_sales row was already closed out) reset its counters to zero and then did nothing else — falling through to `return false` without ever inserting a row. Completed to share the same accumulate-and-insert path as any other sale, just starting from a zero baseline. Verified live: a sale placed right after `cashup` now succeeds and stock still decrements correctly.
- **`update_stock()` could only ever set a barcode's stock once.** It always ran a plain `INSERT INTO store.stock`, which fails with a duplicate-key error against the table's `UNIQUE(barcode)` constraint for any barcode that already has a row — i.e. every stock movement after a product's first. Same bug, independently, in `move_stock_in()`/`move_stock_out()`. All three now use `INSERT ... ON CONFLICT (barcode) DO UPDATE`. Also fixed a copy-paste bug in `update_stock()` where the "available" baseline was read from `jStock["quantity"]` instead of `jStock["available"]`, silently corrupting the sellable-stock figure on every movement.
- **`cash_up()` crashed the entire CGI process** (`std::invalid_argument` from `std::stod("")`, uncaught — confirmed via `terminate called after throwing an instance of 'std::invalid_argument' / what(): stod`, exit code 134/SIGABRT) whenever no `till_float` row had ever been set (e.g. a fresh install, before anyone runs `setfloat`). The HTTP response was a 200 with a completely empty body, since headers were flushed before the crash. Fixed with a length-checked default.
- **`taxsummary` crashed the same way** — `SUM(total_value)` over zero matching orders comes back in a form (empty, or the literal 4-character text `"null"` via this codebase's JSON layer) that a `.length() > 0` guard alone doesn't catch before handing it to `std::stod`. Added a shared `safe_stod()`/`safe_stol()` helper (catches and defaults rather than propagating) and applied it to every report function's aggregate-derived numeric parsing (`get_tax_summary`, `get_revenue_report`, `get_inventory_report`). **This class of bug (uncaught `stod`/`stol` on empty/`"null"` DB results, or on unvalidated client input like `sellitem`'s `price` or `webstoreorder`'s `total`) was not exhaustively swept — only the report-path instances that were actually hit during this session's testing were fixed. A caller sending a non-numeric `price`/`total`/`quantity` to several commands can very plausibly still crash the process; flagged for the dedicated review.**
- **`inventoryreport` emitted invalid JSON** (`"unit_price": ,` — a value-less key) because it read `jItem["price"]` when the underlying query selects `p.rs_price` with no alias. Fixed to read the right key. Same class of bug also found and fixed in `get_dashboard()` (`jDailies["modified_date"]` — the query selects `cashup_date`, never `modified_date`) and `complete_stock_take()`/`get_inventory_report()` (`jData["supplier_encrypt"]`/`jItem["supplier_encrypt"]` — the query selects plain `supplier`).
- **`get_details()` (the `getdetails` command, product lookup/search used by both frontends) referenced a `modified_date` column that doesn't exist anywhere in the schema** (`store.products` has `updated_at`). Every call failed outright. Fixed to use the real column name.
- **`get_sales_report()`'s query was fundamentally invalid** — it selected `product_description` and a `price` column directly from `store.period_sales`, neither of which exists there (only `store.products` has `product_description`; there is no `price` column anywhere in `period_sales`, and the query had no join to `products` at all). Fixed by joining `products` and computing revenue as `quantity × current unit price` — an approximation, not the same thing as the actual sale-time price (this schema doesn't track price-at-sale-time; see the ledger-semantics note below).

### 0.3 What this explains from the original audit, and what's newly found

- The original audit's §3.13 finding (a hardcoded credential pair in public storefront JS that "doubles as a real database credential") is now understood precisely: it worked *only* because of the connection-pool bug in §0.1 — the pool ignored per-instance credentials and always handed back the first-seeded (service-account) connection, so the storefront's hardcoded pair never actually needed to be a real Postgres login role for anything to work. That's fixed now (§0.1), so this specific mechanism no longer applies — but the hardcoded credentials themselves are still sitting in `code/web_store/js/cart.js` etc. and still need to be removed/rotated (unchanged from the original audit's priority list).
- **New, significant finding**: `adduser` creates a row in `store.customers` (a completely separate table from `store.users`), but `check_user_credentials()` — the function every single command runs through to authenticate — only ever queries `store.users`. **A customer account created via the public API can never actually authenticate for any command**, including the ones a customer would need (`webstoreorder`, `orderhistory`, `getreceipt`, `validatecart`). Verified live: creating a customer via `adduser` and then calling `webstoreorder`/`orderhistory` as that customer returns `"User is not active on the system"` for every one of them. This is very likely *why* the web store's JS uses one shared hardcoded service-account login for everything (§3.13/§0.3 above) rather than each customer's own credentials — per-customer auth may never have been possible at all with this table split. This needs a design decision (merge into one users table with a role/kind column, or give `check_user_credentials()` a customer-table fallback) rather than a unilateral fix — left for the dedicated review, flagged here as high priority since it affects nearly every customer-facing command.
- `store.period_sales.running_total` is a **cumulative-within-the-current-open-period** figure (each sale inserts a new row carrying the running total so far; `cashup` closes a period by flipping every row's `completed` flag), not a per-row revenue amount — so it cannot be summed across rows to get "revenue for a date range" (this is what made `get_sales_report()`'s original query nonsensical even before considering its missing-column bug). The current fix approximates revenue from current unit price; a correct fix needs either a per-sale price-at-time-of-sale column or a query that understands the open/closed period boundaries. Left for the dedicated review rather than guessed at further.
- Confirmed live and unchanged from the original audit: `initiate_payment`/`confirm_payment`/`till_card_sale`/`process_refund` still do not touch the database at all (§3.11) — no persistence was added in this pass, since that's a feature gap (deciding the right schema/transaction shape for payment records) rather than a bug in existing code.

### 0.4 Boudica AI integration (getadvice / stockanalysis / salesanalysis) — wired up, two more bugs found and fixed only by running it end-to-end

Same broad effort as §0, across two sessions (2026-09-08 initial wiring, 2026-09-09 the two fixes below). `call_boudica()` (`main.cpp`) now calls the real Boudica SLM `/chat` API (`request_domain`/RAG-aware) via `Http::post_json()` (libcurl — replaced a `popen()`+shell-`curl` RCE, see the now-fixed §3.10 below) instead of the wrong `{"prompt": ...}` field name it originally shipped with (real field is `message`). Added `get_stock_analysis()`/`get_sales_analysis()` (new `stockanalysis`/`salesanalysis` commands) that embed the existing inventory/sales report JSON into a prompt and ask Boudica to analyze it.

**Two bugs found and fixed only by testing against a real, reachable Boudica SLM deployment** (both looked fine from a static read — `getadvice` returned `{"response": "Could not get a response from the AI system."}` even though a manual `curl` from inside the same container, same URL/payload/headers, worked):

- **The hand-rolled `JSON<>` parser (`jsonobject.h`) silently corrupts on real AI answers.** It splits on the first unquoted-looking comma/colon it finds without tracking whether it's inside a string value. Boudica's answers are free-form HTML/markdown (list items like `<strong>Safety Stock Optimization:</strong>`, parentheticals like `(e.g., ...)`) — every such comma/colon gets misread as a new key/value boundary, and the parser eventually hits one of its several `keys.clear(); values.clear();` corruption-recovery paths, wiping out even the already-correctly-parsed `"response"` key. A short punctuation-free reply (e.g. "Hello! How can I help?") parses fine, which is why this was easy to miss. Fixed by adding `extract_json_string_field()` (`main.cpp`), a small quote/escape-aware scanner used only for pulling `"response"` out of Boudica's reply — deliberately not a fix to the general-purpose `JSON<>` class itself, which is used elsewhere in the codebase and out of scope here.
- **`call_boudica()` read `BOUDICA_HOST`/`BOUDICA_PORT`/`BOUDICA_API_KEY` via `std::getenv()`, which is always null/empty at request time.** CGI scripts run under Apache's `mod_cgid` do **not** inherit the server process's arbitrary OS/Docker environment — confirmed live: `/proc/<pid>/environ` for the Apache/cgid daemon processes correctly shows the Docker-supplied `BOUDICA_*` vars, but a debug `getenv()` print from inside an actual CGI request showed all three as null. Without `PassEnv` directives (none configured), only Apache's derived CGI meta-variables reach the script. With the host/port defaulting to `localhost:80`, `call_boudica()` was silently hitting boudica_pos's *own* Apache instance and getting back a `404 Not Found` HTML page instead of Boudica's JSON — which the (also-broken) parser above then turned into an empty string. This is exactly why every other piece of runtime config in this codebase (DB host, admin credentials, Stripe key) already goes through `boudica_pos.conf` (rendered once from env vars by `docker/backend/entrypoint.sh` via `envsubst`, read via `get_configuration()`) instead of `getenv()` — `call_boudica()` now follows the same pattern. Added `boudica_host`/`boudica_port`/`boudica_api_key` to `docker/backend/boudica_pos.conf.template` and `get_configuration()`.

Verified live end-to-end (2026-09-09, against this box's real running Boudica SLM `product_templates/multiuser` deployment with a genuine `bdk_...` test API key): `getadvice`, `stockanalysis`, and `salesanalysis` all now return real AI-generated text through the full container stack, not just via a manual curl bypassing the app.

**New, non-blocking finding, not fixed**: `stockanalysis`/`salesanalysis` do correctly embed the real inventory/sales JSON into the prompt (verified by reading the prompt-building code, not just output) but Boudica's replies for both commands say things like *"the provided JSON data appears to be incomplete... please provide the full JSON structure"* — i.e. the model doesn't seem to trust or use the inline embedded JSON as data, plausibly because its own system prompt prioritizes RAG-retrieved/"grounded" documents over literal inline JSON in the user message. This is a prompt-engineering/AI-behavior issue on the Boudica SLM side, not a boudica_pos code bug — flagged for whoever tunes the analysis prompts next, not chased further here.

### 0.5 The entire hand-rolled JSON layer (both directions) replaced with nlohmann/json (2026-09-09)

At the user's request: `jsonobject.h`'s `JSON<std::string,std::string>` class (the parser behind §0.4's bugs, written a long time ago) split on the first unquoted-looking comma/colon/brace it found without tracking string boundaries — it wasn't a JSON parser so much as a best-effort punctuation scanner, and every value containing a comma or colon (essentially any real product description, address, or AI-generated text) was a latent corruption risk. Investigating turned up that the problem went one level deeper: `pgresultToJson()` (`postgresbc.cpp`), which turns every Postgres query result into "JSON" for the rest of the app, never produced *valid* JSON in the first place — single-row results were double-brace-wrapped (`{{"col":"val"}}`), multi-row results were bare `{...},\n{...}` blobs with no enclosing `[...]` array, and no string value was ever escaped (a quote or backslash in any DB column already broke output). The custom parser only "worked" because it was equally loose about structure — real JSON tooling can't read what it was emitting.

**Scope**: the whole read *and* write side of the JSON boundary, not just the parser class.

- `pgresultToJson()` now builds a real `nlohmann::json` value and `.dump()`s it, using `PQgetisnull()` for genuine NULLs. Same shape *contract* callers already relied on (0 rows → one object with every column present as `""`; 1 row → a bare object; >1 rows → a JSON array) — just valid syntax now. (Incidental fix: the error-path branch had an always-false condition — `res.find("}") != npos` on a string that was always just `"{"` at that point — so a query error previously returned a bare, unclosed `"{"`; now correctly returns `{"Success": "Fail", "message": "..."}`. Low practical impact, since most callers check `getLastError()` before ever looking at the response text.)
- Two small shared helpers (`includes/json_utils.h`): `json_row()`/`json_rows()` normalize a `pgresultToJson()`-shaped string (or an already-parsed nested value) into "the row" or "every row" regardless of which shape came back; `json_str()` reads a field defaulting to `""` (matching the old parser's default-empty behavior) without ever calling `.dump()` on a failed/discarded parse (which nlohmann refuses to serialize). `json_parse_or_raw()` is used wherever an externally-sourced JSON blob (a Boudica reply, a client-supplied cart) gets re-embedded as a nested value in a response — falls back to a plain string of the raw text rather than injecting an invalid value if the source didn't parse.
- Every one of the ~49 `JSON<>` read call sites (main.cpp + authentication.cpp) and the ~21 manual `resp.find("{")`/`find("}")` loops that faked array iteration over the old broken output are migrated to real parsing/iteration. `check_user_credentials()`'s hand-built `{"response": [...]}` wrapper (previously built via string concatenation and `{{`→`{` replacement hacks to route around the old parser) is now built directly with nlohmann.
- Every hand-built *outgoing* response in `main.cpp` — ~143 `std::cout << "{...}"` statements and ~55 `return "{...}"`-shaped returns across the ~36 dispatched commands — is migrated to building a `nlohmann::json` object/array and emitting it via one `.dump()`. Two small helpers (`emit_json_response()`/`emit_json_error()`) cover the very common single-field `{"response": "..."}`/`{"error": "..."}` shape used by most command handlers. This incidentally fixed several concrete bugs found while doing it: at least four handlers (`sellitem`, three `pricelookup`-style "required fields" checks) were emitting invalid JSON due to a missing closing quote before `}`; `validate_cart_inventory()`'s response had a duplicate `"valid"` key (JSON's last-key-wins meant the second one was always the one that counted, so behavior is unchanged, just no longer duplicated); `complete_stock_take()`/`get_details()`'s streamed output used a fragile "peek ahead in the remaining unparsed text for another `\"barcode\"`" trick to decide whether to print a trailing comma, which could emit an invalid trailing comma before `]` when later candidate rows existed but were filtered out — building the array in memory removes the need for that trick entirely. `call_boudica()`'s outbound request payload and the Stripe `metadata` fields in `initiate_payment`/`till_card_sale` (previously also hand-built strings, with the same unescaped-caller-input risk) are built the same way.
- `json_escape()` and `jsonobject.h` are both deleted — fully unused once every call site above was migrated.
- One deliberate non-fix, to keep this pass to JSON-layer changes only: `get_dashboard()`'s per-day-breakdown loop has a pre-existing `daily != "" || daily != "null"` condition that's always true (should very likely be `&&`) — left exactly as-is (just re-expressed over real JSON) rather than "fixed" as a drive-by, since it changes runtime behavior beyond what this migration set out to do. Left in a comment at the call site; flagged here too.

Verified live (2026-09-09) against the running container: rebuilt cleanly on the first attempt (`nlohmann-json3-dev` added to `docker/backend/Dockerfile`, `find_package(nlohmann_json)` in `code/back_end/CMakeLists.txt`), then exercised a broad sweep of commands end-to-end — reads (`getsupplierlist`, `getworkshops`, `getdashboard`, `inventoryreport`, `getdetails`, `salesreport`, `revenuereport`, `taxsummary`, `validatecart`, `login`, `pricelookup`, `quantitylookup`), writes (`stocktake`, `completestocktake`, `addinvoice`, `setfloat`, `sellitem`, `cashup`, `addproduct`, `updatestock`, `adduser`), the AI-backed commands (`getadvice`, `stockanalysis`, `predict_reorder_date`), the Stripe-backed commands (`initiate_payment`, `till_card_sale`), and the customer-order flow (`webstoreorder`, `getreceipt`, `orderhistory`) — every one returned valid, correctly-typed JSON (numbers as numbers, not quoted strings, wherever the original hand-built output was already unquoted). No new crashes or corrupted output; the failures that did surface are pre-existing bugs unrelated to this migration, now visible as clean JSON instead of silently corrupting or crashing:
- `predict_daily_sales`/`predict_weekly_sales` (`forecast_daily_sales()`/`forecast_weekly_sales()`, `main.cpp`): the underlying SQL selects pure aggregates (`SUM`/`COUNT`/`AVG`) with no `GROUP BY`, then `ORDER BY sale_date` — invalid SQL, fails with a Postgres error every time. Pre-existing, not touched by this pass — flagged for the dedicated review.
- `till_card_sale`: unlike `initiate_payment`, it has no `stripe_key.empty()` guard and doesn't check whether `stripe.createPaymentIntent()` actually succeeded before reporting `{"success": true, ...}` — pre-existing, flagged for the dedicated review.
- `webstoreorder` as tested (using the seeded `admin` account rather than a real customer) hit the `store.customers` foreign-key gap already documented in §0.3 — expected, not a new finding.

## 1. System Overview (verified)

Boudica POS is a single-tenant EPOS system, three parts:

- **Backend** (`code/back_end/src`, also mirrored in `github/src`): one C++20 binary run as a **CGI program** (not a persistent REST daemon — reads `QUERY_STRING`/stdin per invocation, `main.cpp:2245-2260`), dispatched by a giant `if/else if` chain on a `command` string parameter (`main.cpp:2420-3241`, ~34 commands). Talks to PostgreSQL via `libpq` (`postgresbc.cpp`). Stripe integration in `stripe.cpp`/`stripe.h`. Custom hand-rolled JSON parser (`includes/jsonobject.h`), no external JSON library.
- **Till dashboard** (`code/web`): vanilla JS, 11 tabs, talks to `/cgi-bin/boudica_pos`. Real USB barcode-scanner keystroke capture (`scripts/till.js:7-22`), real Star WebPRNT SDK printing (`scripts/printer.js`, vendor SDK vendored in `scripts/star/`).
- **Web store** (`code/web_store`): vanilla JS ES6 modules + several pages with inline scripts, talks to the same backend, plus a separate unrelated `pgbc.js`/`api.js` driver pair that targets a *different* CGI endpoint (`/cgi-bin/pgbcadmin` — this looks like reused boilerplate from OmniIndex's other product, not actually POS-specific; `epos.js` and `cart.js` are the real storefront drivers).
- **Database**: PostgreSQL, schema in `code/sql/setup.sql` — 19 tables (`suppliers`, `suppliers_payments`, `suppliers_invoices`, `products`, `stock`, `stock_take`, `stock_removal`, `period_sales`, `till_float`, `cash_up`, `customers`, `customer_orders`, `payment_transactions`, `reward_points`, `web_store_front`, `workshops`, `audit_log`, `users`, `logs`).
- No `LICENSE` file exists anywhere in the tree despite being described as MIT-licensed.

## 2. What Genuinely Works

- Barcode scan → lookup → cash sale → stock decrement → Star printer receipt: the JS side of this is real, end-to-end (`till.js`, `printer.js`) — **but see §3.0: the backend it calls is broken for any product that already has a stock row, which is every product after its first stock entry.**
- Web store: product search (`epos.js:SearchStore`), cart validation against live stock (`cart.js:117-144`, `validatecart` command), order submission (`cart.js:284-320`, `webstoreorder`), order history (`order-history.html:344+`, `orderhistory`), receipts (`receipt.html:379`, `getreceipt`) — all real backend calls, not mocked.
- Stripe payment intents/confirmation on the **web store** checkout is wired end-to-end: create intent → `stripe.confirmCardPayment` → backend `confirm_payment` (`stripe-checkout.js:143-165`). Stripe webhook **signature verification** logic is genuinely implemented with HMAC comparison (`stripe.cpp:205-246`).
- AI forecasting commands (`predict_daily_sales`, `predict_weekly_sales`, `predict_monthly_sales`, `predict_reorder_date`) and `getadvice` (Gemini) are real handlers in `main.cpp:3142-3282` / `2791`, not stubs.
- Reporting commands (`salesreport`, `revenuereport`, `inventoryreport`, `taxsummary`) run real SQL aggregation (`main.cpp:2868-2947`).

## 3. Critical Gaps the Existing Docs Don't Mention

These are functional/security defects found by reading the code, not "missing feature wishlist" items — they mean parts of the system marked "✅ COMPLETE" in the other docs are not safe or not fully working as shipped. **§3.0 was found only after actually running the stack in a container against a real Postgres instance** — it did not surface from reading the C++ alone, and is the single most severe functional defect in this codebase: it breaks the core sale-recording path, not a peripheral feature.

### 3.0 `sellitem` cannot process a sale for any product that already has a stock row — i.e., almost never works
Confirmed by running an actual `sellitem` call end-to-end against the schema in `code/sql/setup.sql` and reading the resulting Postgres errors directly (not the generic message the API returns):

1. **`update_sale()` builds a syntactically invalid INSERT** (`main.cpp:1009`): a missing closing quote after the `supplier` value merges it with the next several fields into one malformed string literal. The actual SQL sent is e.g. `INSERT INTO store.period_sales (...) VALUES ('Demo Supplier,8.990000,0,'5000000000001','cash','1');` — Postgres rejects this outright: `ERROR: syntax error at or near "5000000000001"`. The failure is caught (`main.cpp:1025-1027`) but **not treated as fatal** — the function closes the connection and keeps going anyway, so this corrupt-SQL failure is silent from the caller's perspective.
2. **`update_stock()` only ever does a plain `INSERT`, never an `UPDATE`** (`main.cpp:812`): `INSERT INTO store.stock (quantity, available, barcode) VALUES (...)` — even though the function just SELECTed the existing row (`main.cpp:757`) specifically to compute the new quantity as a delta. Because `store.stock.barcode` is `UNIQUE` (`setup.sql`), this insert fails with `duplicate key value violates unique constraint "stock_barcode_key"` for every barcode that already has a stock row — which is every product after its first stock entry, i.e. essentially all real usage. This failure **is** treated as fatal (`main.cpp:816-819`, correctly returns `false`), which is why `sellitem` surfaces as a hard error to the caller.

Net effect: a product can receive stock exactly once (its very first `INSERT`); every subsequent sale, restock, or stock-take completion targeting that same barcode fails, because none of those code paths ever `UPDATE store.stock` — they all reuse this same insert-only `update_stock()`. This is not a till-frontend problem (the JS side genuinely does call the right commands, per §2) — it is the backend's core stock/sales-ledger logic that does not work against its own shipped schema. Any prior "core POS is production-ready" assessment (including in `README.md`/`MISSING_FEATURES_ANALYSIS.md`) is not supported by actually exercising the code.

### 3.1 SQL Injection — pre-authentication, exploitable via plain GET
`check_user_credentials()` (`main.cpp:369-374`) and `Authentication::authenticate()` (`authentication.cpp:21-24`), `getUserById`, `getUserByUsername`, `hasRole`, `verifyPassword`, `updateLastLogin` (`authentication.cpp`, all methods) build SQL by raw string concatenation of the `username`/`password` request parameters — **no escaping, no parameterized queries** (`postgresbc.cpp` has no `PQescapeLiteral`/`PQexecParams` anywhere). This function gates *every single command* (`main.cpp:2407-2408`), so it's the front door: a crafted `username` or `password` query-string value can attempt classic SQLi against the auth query itself. A partial, inconsistent sanitizer (`clean_value()`, `main.cpp:149-156`, strips `,"'()`) is applied to *some* other fields (product description, supplier, invoice details) but not to `barcode`, `rs_price`, `username`, `password`, or several others — so the mitigation is incomplete even where present.

### 3.2 Authorization is fake — every logged-in user is treated as admin
`Authentication::authenticate()` hardcodes `result["role"] = "admin"` for **any** successful login regardless of the DB row's actual role (`authentication.cpp:47`, marked `// TODO: Parse from JSON response`). `Authentication::hasRole()` runs a `COUNT(*)` query, **discards the result**, and unconditionally `return true;` (`authentication.cpp:112-124`) — role checks always pass. Command dispatch in `main.cpp` only checks `is_active` (`main.cpp:2410-2414`), never role — so any active credential (staff, till, or the web store's own service account, §3.3) can call `adduser`, `addsupplier`, `revenuereport`, `taxsummary`, `process_refund`, etc. There is no staff/admin privilege separation despite it being listed as a completed feature ("Role-Based Access (staff levels)") in `MISSING_FEATURES_ANALYSIS.md`.

### 3.3 Hardcoded service credentials shipped in public JS, pointed at a live demo server
The web store hardcodes `username: 'web_store_user', password: 'web_store_pass'` directly in client-side source, used for `validatecart` (`cart.js:126-127`), `webstoreorder` (`cart.js:296-297`), `orderhistory` (`order-history.html:371`), `getreceipt` (`receipt.html:379`), and **`salesreport`/`revenuereport`/`inventoryreport`/`taxsummary`-capable `reports.html:466`** — all sent to a hardcoded `https://demo.pgbc.ai/cgi-bin/boudica_pos` (`epos.js:7`, `cart.js:132`, `order-history.html:376`, `reports.html:472`). Anyone who views-source on the public storefront gets a working credential that, per §3.2, has no role restriction — meaning a member of the public can pull full financial reports (revenue, margins, VAT) and potentially call admin commands, and every unconfigured deployment of this open-source project silently sends customer traffic to the vendor's own demo instance until someone edits the source.

### 3.4 Card payments on the till never complete the sale
`handlePayment()` in `till.js:425-447` opens the Stripe card modal and **returns immediately** — `updateStockForTransaction` (stock decrement/`sellitem`), receipt printing, and `clearSale()` are only reached for cash/other payment methods. `till-card-payment.js`'s success handler never calls back into `till.js`. Net effect: a successful card charge on the till doesn't decrement stock, doesn't print a receipt, and doesn't clear the till for the next sale. Also both `till-card-payment.js:7` and `stripe-checkout.js:7` ship a hardcoded placeholder `STRIPE_PUBLISHABLE_KEY` (`pk_test_...`) with a `// TODO: Set to actual key from config` — Stripe is non-functional until someone edits source, there's no config-driven key injection.

### 3.5 No Stripe webhook endpoint despite webhook-verification code existing
`stripe.cpp:205-246` implements signature verification for incoming Stripe webhooks, but grep confirms **no command in `main.cpp` ever calls it** — there's no webhook receiver at all. Payment state only updates when the browser tab stays open long enough to call `confirm_payment` client-side; a closed tab, failed redirect after 3-D Secure, or a refund/dispute actioned from the Stripe dashboard will never reach the store's database. This is a materially different (and more specific) problem than the "payment reconciliation dashboard" bullet in `MISSING_FEATURES_ANALYSIS.md`.

### 3.6 Credentials-in-URL and plaintext localStorage password, everywhere
Every API call across both the till (`till.js`, `login.js`, `dashboard.js`, `stock_take.js`, `add_stock_item.js`, `show_products.js`) and web store sends `username`/`password` as **plaintext GET query-string parameters** — logged in web server access logs, browser history, and any intermediate proxy. The till additionally stores the password in plaintext `localStorage` (`login.js:2-3, 62-63`) and reads it back for every request.

### 3.7 Stored-XSS chain
Product/order data is rendered via unescaped `innerHTML` template literals in multiple places (`show_products.js:42`, `app.js:46,89`), and the AI advice response is explicitly rendered raw: `messageElement.innerHTML = htmlContent; // response is expected to be formatted HTML from the API` (`app.js:118-119`). Because `addproduct`/`addsupplier` accept attacker-reachable text (§3.3 gives an anonymous caller a valid credential to call these), and because the till stores the password in `localStorage` (§3.6), a crafted product description or a prompt-injected AI response can chain into full credential theft from a staff member's till session.

### 3.8 CORS wide open + disabled IP allowlist
Every response sends `Access-Control-Allow-Origin: *` (`main.cpp:2177`). The `server_whitelist` IP-allowlist check has its result unconditionally overridden right after being computed: `is_white_listed = true;` sits on its own line immediately before the `#endif` regardless of the check above it (`main.cpp:2281`), so the allowlist is dead code.

### 3.9 Email is fully simulated
`sendEmailReceipt`-equivalent in `cart.js:245-277` literally does `console.log("--- SIMULATING EMAIL RECEIPT ---")` — there is no email transport anywhere in the codebase (matches what the existing docs claim as "missing", confirmed accurate here).

### 3.10 Remote command execution via `getadvice` (shell injection, pre-auth given §3.1)
`getadvice` (`main.cpp:2791-2804`) takes the raw `prompt` parameter (only URL-decoded) into `get_advice()` (`main.cpp:1527-1535`) → `call_boudica()` (`main.cpp:44-68`), which builds a shell string `"curl ... -d '" + payload + "'"` (`main.cpp:64`) and runs it via `popen()` (`Utils::exec()`, `utils.cpp:335-340`). A single quote in `prompt` breaks out of the shell string — arbitrary command execution as the CGI process user. Combined with the auth bypass in §3.2/§3.8, this is reachable with no valid credentials at all.

### 3.11 Payments are never persisted — `payment_transactions` is a phantom table
None of `initiate_payment`, `confirm_payment`, `till_card_sale`, or `process_refund` write to the database (`main.cpp:2960-3141` — no `runCommand`/insert in any of these blocks), despite `store.payment_transactions` (`setup.sql:183`) existing with full Stripe fields for exactly this purpose. `till_card_sale` generates its `till_trans_id` with `rand()` (`main.cpp:3086-3105`) and returns it without saving it anywhere — the ID is unrecoverable the moment the response is sent. This is a different, more severe problem than "no reconciliation dashboard" (as the older docs frame it): the system has no record of card payments at all beyond what Stripe itself retains.

### 3.12 No server-side price recomputation — client-supplied total is trusted
`initiate_payment`/`till_card_sale` take `total`/`total_value` straight from the request (`std::stod(total_value)`, `main.cpp:3001/3091`) and create a Stripe PaymentIntent for that amount with no recomputation from the actual cart/item prices server-side. A caller (including the future external POS integration) can request a PaymentIntent for any amount it likes, decoupled from what's actually in the order.

### 3.13 Hardcoded near-production credentials in public storefront JS, feeding a raw-SQL executor
`code/web_store/js/data.js:10-11` hardcodes `creds.User('sibain@omniindex.io')` / `creds.Password('Ch35t3rP455w0rd')` (comment: "Only for testing on an none whitelist box") and uses them against `driver/pgbc.js`, a generic string-interpolated-SQL-over-HTTP executor hitting `/cgi-bin/pgbcadmin` — a different, more powerful admin endpoint than the POS API itself. If that account has real database privileges, this is a full database compromise reachable by anyone who views-source on the storefront.

### 3.14 Schema-level defects
- `code/sql/setup.sql:2` hardcodes a plaintext database password (`Th3Cur1051tyP455word`) in a source file destined for an MIT-licensed public repo.
- `period_sales` (`setup.sql:109-121`) declares indexes with inline `INDEX idx_...(...)` clauses inside `CREATE TABLE` — this is MySQL syntax; it is not valid PostgreSQL DDL and will fail outright when this schema file is run against Postgres (the same file elsewhere uses `CREATE EXTENSION vector`, confirming Postgres is the actual target).
- `search_functions.sql` defines six real, usable functions — `search_products_fulltext`, `search_products_semantic`, `search_products`, `search_by_barcode`, `search_by_supplier`, `get_low_stock(threshold)` — none of which `main.cpp` ever calls. The touted "full-text/semantic search" and a ready-made low-stock-alert query both exist in the database layer and are wired to nothing in the API.
- `reward_points` (loyalty) and `workshops` beyond read-only listing are similarly present in schema with zero write-path code, confirming §4's "table only" status independently.

### 3.15 Outbound TLS verification disabled + another hardcoded API key
The geo-IP lookup in `http.cpp:55` hardcodes a RapidAPI key in source, and the same call disables certificate validation entirely — `CURLOPT_SSL_VERIFYPEER, 0L` / `CURLOPT_SSL_VERIFYHOST, 0L` (`http.cpp:58-59`) — a man-in-the-middle exposure on that outbound request.

### 3.16b `getdetails` is broken against the shipped schema (found by actually running it)
`get_details()` (`main.cpp:1085` and `main.cpp:1117`) orders its product-lookup queries by `p.modified_date` / `modified_date`, a column that does not exist anywhere in `code/sql/setup.sql` — `store.products` only has `updated_at`. Every `getdetails` call (product lookup/search, used by both the till's Lookup tab and the web store's search box) fails outright with a Postgres error. This wasn't visible from static reading of `main.cpp` alone — it only surfaced once the schema was actually instantiated and exercised end to end. Patched at container-build time (`docker/backend/Dockerfile`) by rewriting the column name; the tracked source is left as-is.

### 3.16 POST body silently truncated at 4095 bytes
The CGI POST body reader uses a fixed buffer and never checks `Content-Length` for overflow (`main.cpp:2248-2250`). A large cart/order payload (many line items, as a busy till or a bulk API-driven order from the planned POS integration would send) is silently truncated rather than rejected — the request will parse whatever partial JSON/query-string survives the cut, which is a correctness landmine, not just a size limit.

## 5. Implications specifically for the planned POS-as-external-API-caller integration

The new POS system is meant to call this backend as a pure API client — no shared session, no shared codebase. That framing makes several of the above worse than they'd be for an internal integration:

- **There is no real API authentication scheme to integrate against.** The existing model is "resend a username/password as a GET query-string param on every call," gated by an auth check that's SQL-injectable (§3.1) and bypassable by omitting credentials entirely (§3.8), behind a role system that always reports back `admin` (§3.2). An external POS should not be pointed at this as-is; it needs a real API-key/token layer added first, or the POS becomes the easiest path to fully compromising the backend.
- **Financial integrity matters more from an external caller.** §3.11 (payments not persisted) and §3.12 (client-supplied total trusted) mean a POS integration could not currently produce an auditable, tamper-resistant record of what it charged — every payment's source of truth would live only in Stripe, not in Boudica's own database.
- **The 4095-byte POST truncation (§3.16)** will bite a POS sending structured multi-item orders/carts as JSON, in a way it wouldn't for the existing till (which sells mostly one item at a time via query params).
- **CORS being `Access-Control-Allow-Origin: *`** (§3.8) is actually *convenient* for a cross-origin API caller with no cookies involved — but it should be paired with real per-request authentication, which is currently missing, not with the fake whitelist that exists today.

## 6. Recommended Priority Order

1. **Fix authentication/authorization before anything else** — parameterize all SQL (switch to `PQexecParams`), make `hasRole()` actually check the query result, stop hardcoding `role = "admin"` on every login, add per-command role gating in the `main.cpp` dispatch, and remove the unconditional `is_white_listed = true` override.
2. **Design a real API-key/token scheme for the planned POS integration** rather than reusing the credentials-in-query-string model — this is a new external caller, not more internal code, and needs its own auth boundary.
3. **Remove hardcoded credentials** from the storefront source (`web_store_user`/`web_store_pass` in `cart.js` etc., and the `sibain@omniindex.io`/`Ch35t3rP455w0rd` pair in `data.js`) **and the demo-server URL**; make backend URL and any service credentials deployment-time config, not committed literals. Rotate any of these that may have been real.
4. **Close the RCE in `getadvice`** (§3.10) by calling the Gemini/Boudica HTTP API directly via libcurl instead of shelling out through `popen()`.
5. **Make payments durable**: write `payment_transactions` rows on `initiate_payment`/`confirm_payment`/`till_card_sale`/`process_refund`, recompute totals server-side from cart contents, and wire the existing webhook-signature verifier to an actual endpoint.
6. **Fix the till card-payment flow** to actually finish the sale (stock, receipt, clear).
7. **Stop sending credentials in URLs**; move to POST + a real session/token scheme instead of resending username/password on every call, and stop storing the password itself in `localStorage`.
8. **Escape/encode all `innerHTML` insertions** of backend-sourced data (product descriptions, AI responses) to close the stored-XSS chain.
9. **Fix the schema bugs** (§3.14): the MySQL-syntax `INDEX` clause in `period_sales` that breaks on Postgres, and either wire up or remove the six orphaned search functions.
10. Then tackle the feature gaps in §4, roughly in the order: discounts → returns workflow completion → reordering/PO generation → email notifications → loyalty → multi-location.
